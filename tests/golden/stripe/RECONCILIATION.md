# Reconciliation — Stripe

Generated by Vault-Payments from manifest data verified 2026-10-21.

Reconciliation exists because **webhooks are not a guarantee**. Providers retry,
but your service can be down, redeploying, or slow, and a missed event looks
exactly like a paid order that never progressed. The rule is:

> The provider is the source of truth. Local state is a cache that must be
> checked against it.

## What the generated code already does

- **Durable dedupe.** Every accepted event is inserted into a SQLite table whose
  `event_id` is a `PRIMARY KEY`. A repeated delivery returns success without
  reprocessing, so a provider retry can never double-apply.
- **Persist before acknowledge.** The event is stored, then `200` is returned.
  A crash between those two steps loses nothing: the event is already durable.
- **Asynchronous processing.** Business logic runs after the event is stored and
  never affects the HTTP response. A handler that fails is marked `failed` in
  the store with its error, so it can be found and replayed.

## How to detect a missed event

Missed events are found by comparison, not by waiting:

1. **Poll the provider for authoritative state.**
   `GET /v1/payment_intents/{id}` returns the current status of a payment. Treat this
   as the truth, not your local record.
2. **Compare against your local ledger.** Any payment that is locally
   `pending` but provider-side complete, or vice versa, is a discrepancy.
3. **Drive the correction from the fetched state**, not from the missed event.
   A re-delivered webhook is convenient but never required.

## Replay and recovery

- Failed processing is recorded with its error in the `webhook_events` table
  (`status = 'failed'`). Query for those rows and re-run business logic; do not
  wait for the provider to re-send, because it may consider the delivery
  acknowledged.
- This provider does **not** replay automatically. To recover a specific event,
  use the events list or a dashboard resend — but prefer re-fetching the
  underlying object, which is cheaper and idempotent.

## Idempotency

Retrying a payment operation must never double-charge:
- `authorize` sends `header` idempotency via `Idempotency-Key`.
- `capture` sends `header` idempotency via `Idempotency-Key`.
- `void` sends `header` idempotency via `Idempotency-Key`.
- `refund` sends `header` idempotency via `Idempotency-Key`.
- `status` is a read and is inherently safe to repeat.

## Operationally

- Back up the event database. It is the record that an event was seen.
- Monitor `status = 'failed'` and `status = 'pending'` age. An event pending for
  longer than the provider's retry window usually means processing is stuck.
